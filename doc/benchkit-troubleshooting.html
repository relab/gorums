benchkit — Troubleshooting & Log Analysis

How to read a failed or anomalous sweep run: the run lifecycle, the diagnostic artifacts, the failure taxonomy, and a catalog of failure classes with their causes and remedies.

Companion to benchkit.html  ·  gorums repository  ·  doc/benchkit-troubleshooting.html

Start here when a run fails. Every run leaves machine-readable artifacts you can inspect without grepping sweep.log:

  • <base>.manifest.json — status plus failure_phase (setup / measurement / collection), collected_files, missing_files, node_map, and degraded-node flags (§2).
  • logs/<base>.log — every node's output for that one run, interleaved in chronological order.
  • logs/<base>_snapshot.txt — a per-host snapshot (load, fd limits, sockets, surviving processes) captured at the moment of failure.

Read the manifest first: failure_phase plus collected_files classifies the run (§3), the per-run log gives the cross-node timeline, and the snapshot gives host state. sweep -explain automates exactly this reading (benchkit §15).

1. Run lifecycle & exit synchronization

cmd/sweep connects to each host via SSH, deploys the benchmark binary, and launches one process per node for each parameter combination. The binary handles its own distributed coordination; the sweep only launches, monitors, and collects. Knowing which phase a run died in is the first classification step, so the phases are worth internalizing:

Sweep preflight (once per sweep). -netcheck (on by default) has every host ping its ring successor and aborts the sweep when any link shows ≥ 5% packet loss, catching a hard link fault in seconds before any benchmark time is spent. Note the ring runs on an idle network: a link that only drops packets under load can pass it (§5).
Setup (per run). Lingering processes from a prior sweep are killed (SIGTERM, escalating to SIGKILL), and a port preflight skips the run within ~1 s if a benchmark port is still busy, printing the ss line that names the foreign listener. Each node is then launched over SSH, binds the wildcard address, and enters AwaitReady: an outbound probe that sends each peer round-trip echoes until it responds. The probe is progress-based — each response resets a 20 s stall timer — so a peer that died at startup is reported within ~20 s instead of at the 2-minute overall deadline, named by address with its last dial error. On probe failure the node prints a [diag] self-diagnosis (§4.1). A host whose own listener is unreachable passes its own probe — only outbound connectivity is exercised locally — so that condition surfaces on its peers, whose probes stall naming the host.
Measurement. All nodes run their measurement window simultaneously. Each node writes its .binpb result file when its own window ends.
Exit synchronization (symmetric topology). There is no exit barrier. After finishing its window and trailing flush, a node multicasts a best-effort Done signal to its peers and then waits until every peer has signaled Done or a grace ceiling elapses, whichever comes first (SignalDone / AwaitPeersDoneOrGrace in benchmark/symmetric.go). The ceiling is ExitGrace(N) = min(3s + 300ms×N, 20s). In a healthy run all nodes finish within milliseconds of each other and exit via the Done signals long before the ceiling; the ceiling only matters when a Done never arrives. Because the Done send ignores per-peer errors and the wait always falls back to the ceiling, exit relies only on outbound reachability — the direction that stayed healthy even on hosts with broken inbound (§4.1).
Straggler tolerance. A node that is still running after its peers have finished and closed their listeners will see connection refused or incomplete call errors. Once enough peers have signaled Done that the failing phase could no longer succeed (quorumRunOver / anyPeerFinished), the straggler treats this as the expected end of the run — it stops cleanly and keeps its results — rather than exiting with an error. Failures before any peer has signaled Done are still genuine faults and fail the run.
Collection & manifest. When all processes have exited, the sweep downloads the result files (best-effort even after a failed launch, so partial results are preserved), summarizes what it got, compares every node's throughput and median latency against the run median (-degraded-below 0.5, -degraded-above 2, -degraded-latency-below 0.2) and records the outcome in the manifest. There is no automatic retry: a failed or degraded cell stays visible as such rather than being silently replaced.

2. Diagnostic artifacts

All artifacts live in the run's output directory and are named by the run base (<label>_<bench>_N<n>_W<w>_P<p>[_R<rate>][_r<rep>]), so everything about one run is discoverable from its manifest path alone.

The run manifest — <base>.manifest.json

Written before launch (so the directory is self-describing even when the run fails) and updated with the outcome afterward. Fields beyond the run configuration, timestamp, repository HEAD, and deployed binary:

FieldMeaning
status, error succeeded / failed / degraded, with the launch error text on failure.
failure_phase setup (no results at all), measurement (partial results), or collection (nodes finished but files could not be retrieved). The first thing to read on a failure.
collected_files, missing_files How many expected .binpb files exist, and the basenames of the absent ones — recorded on every terminal path, including success, so full coverage is confirmable from the manifest alone.
node_map Per node: SSH alias, advertised peer address, result file, and Gorums node ID. Needed because sweep resolves aliases to numeric IPs before launch (§4.2), and numeric-IP sorting can assign different node IDs than hostname sorting.
degraded_nodes, tcp_stats Nodes whose measurement fell outside the degradation bounds — too slow, too fast, or with a median latency too low for the round trip the benchmark measures — each with the reason it was flagged, its throughput, and relative_to_median for the metric that tripped, plus every host's TCP counter deltas over the run. Degraded runs are excluded from aggregate plots but kept in per-node figures.
diagnosis The LLM triage verdict when the sweep ran with -explain.

Per-run node log — logs/<base>.log

All of one run's node output (stdout and stderr), interleaved in chronological order, for every run — success or failure. The chronological cross-node ordering is deliberate: the signature of an exit-skew failure is "fast nodes exit, then a slow node hits connection-refused against exactly those nodes", which per-node files would scatter across N files. sweep.log holds only the orchestration narrative (run headers, summaries, errors) and mirrors the console.

Host snapshot — logs/<base>_snapshot.txt

Collected from every host of a failed run, before result collection (whose SSH round-trips would let evidence decay). Per host: uptime, load average, CPU count, fd limits, surviving benchmark processes, and the listener and connection state for each benchmark port (ss -ltnp / ss -tan). TIME_WAIT sockets persist ~60 s after a connection closes, so the snapshot still shows who was talking to whom even though the processes have exited. Best-effort: a snapshot failure never masks the original run failure.

Node-health heatmap

The report's node_health figure (from sweep -plot): hosts × runs, colored by each node's throughput relative to the run median. A sick host shows as a red row across the sweep; a one-off hiccup shows as a single red cell. This is the fastest way to spot the infrastructure faults of §5.

3. Failure taxonomy

Failures fall into three classes, distinguishable from the manifest alone. This taxonomy doubles as the few-shot context for sweep -explain: a distilled form of it is embedded in the triage model's system prompt, so keeping this section accurate improves automated diagnoses, not just human ones.

ClassManifest signatureTypical causes
Type A — setup failure_phase: setup; collected_files: 0 A node stalled in AwaitReady: inbound unreachability, a dead peer process, a busy port that slipped past the preflight. All nodes time out and exit; no results exist.
Type B — measurement failure_phase: measurement; partial collected_files Nodes passed readiness but some failed mid-run: completion skew beyond what the Done/grace exit absorbs, a mid-run crash, or clock-sync failure. The fast nodes' results were collected; the failing nodes' are missing.
Degraded status: degraded; all files collected The run completed but one or more nodes ran far below the run median — almost always a host or link fault, not a gorums bug. Go to §5.

Reading a Type B failure

The pattern to look for in logs/<base>.log: the fast nodes print their throughput results and exit; tens of seconds later the stragglers log quorum call error: incomplete call or dial tcp <peer>:9000: connect: connection refused against exactly the nodes that exited. The errors: 0 variant of the incomplete-call message is the tell that the missing responders were gone, not returning errors. The root cause is whatever made the stragglers slow — check degraded_nodes/tcp_stats in the manifest and the load averages in the snapshot. Note that a rate-limited run with too few workers extends its effective window well beyond the nominal one (the pacer queue drains late), which manufactures exactly this skew; the pacer fall-behind warning in the node log names that condition.

4. Failure catalog

Current diagnostic guidance for the failure classes a sweep can still surface, and the producer contracts the tooling relies on. Each entry describes the log signature to look for and what it points at.

4.1 Readiness-probe diagnosis

A node that cannot reach its peers during setup stalls in AwaitReady and fails the run with outbound peers not ready: no outbound peer responded, naming the unreachable peer by address with its last dial error. A host whose own inbound is unreachable passes its own probe (only outbound connectivity is exercised locally), so that condition surfaces on its peers. When the probe fails the node prints a [diag] self-diagnosis; read it with this table (on a peer of the broken host, expect self-dial ok, pointing the blockage at the named host):

ObservationConclusion
listener bound to shows loopback or an unexpected IP Wrong local bind; fix name resolution or bind the wildcard.
Self-dial fails although the bound address matches the advertised IP Local firewall refusing connections, or the listener died.
Self-dial ok The listener works from the host itself; the blockage is between the peers and this host (network filtering, dropped SYNs, a lossy link — see §5).
Goroutine dump shows stream handlers blocked in AcceptPeer/registerPeer Peer streams reached the server but registration stalled: a gorums bug; open an issue with the dump.
Goroutine dump shows an idle gRPC server No peer connection ever reached the process; gorums is exonerated.

Nodes bind the wildcard address (listener bound to [::]:9000), so a host that maps its own name to 127.0.1.1 in /etc/hosts (the Debian convention on the bbchain hosts) cannot bind its listener to loopback. That convention still traps any other software on these hosts that binds by hostname. Probing caveat: never hold nc -l -k 0.0.0.0 9000 on a host while a sweep runs — with SO_REUSEADDR it coexists with the benchmark listener and intercepts peer connections, invalidating both the run and the probe.

4.2 Peer addressing without DNS

sweep resolves each host alias once, controller-side, to one stable non-loopback IP (rejecting loopback/unspecified/multicast, preferring IPv4) and passes numeric ip:port values in -self/-remotes, so nodes perform no DNS at startup. The SSH alias is kept for launch, filenames, logs, and cleanup; the manifest's node_map records the alias↔address↔node-ID correspondence. This exists because gorums.WithNodeList normalizes addresses with net.ResolveTCPAddr: with hostname peer lists every process did N×N DNS lookups before readiness, and one transient resolver SERVFAIL aborted a process and stalled its peers. Removing DNS from WithNodeList itself remains a gorums API question, tracked in the roadmap (benchkit §17) and in §6.

4.3 Completion skew and the exit grace

Symptom. Type B: fast nodes finish and exit; stragglers later hit connection-refused / incomplete-call / clock sync incomplete: got offsets for k of N peers against the exited peers and the run fails with partial results.

The symmetric exit is a best-effort Done signal plus a grace-ceiling race (§1), with the ceiling at min(3s + 300ms×N, 20s). A straggler whose calls fail against peers that already signaled Done treats that as the expected end of the run and stops cleanly with its results (quorumRunOver/anyPeerFinished), and degraded-run flagging separates "one node was pathologically slow" from "the run is unusable". The straggler's clean stop is also why the flagging is two-sided: a straggler whose window outlives its peers' can report far more operations than they did, which -degraded-above catches. Residual risk: a straggler that has not yet reached its post-window phases when peers exit can still fail, and no grace budget survives a genuinely broken link. When this fires repeatedly the fix is operational: find and exclude the sick host (§5).

4.4 Producer contract: diagnostics to stderr

All diagnostic output in a benchmark binary must go to stderr (in-module code uses benchkit.Logf), and never from code that runs under a lock. Unread stdout fills the SSH channel's 64 KB flow-control window, after which the remote process's write() blocks; a goroutine that blocks while holding a lock then stalls peer registration entirely. sweep drains both pipes into the per-run log, so the transport is safe from both ends, but the stderr rule is what keeps a foreign binary safe under any launcher that drains only stderr.

4.5 Operational checks and footguns

  • Busy ports and stale binaries. A busy benchmark port is skipped by the per-run port preflight in ~1 s with a message naming the listener; a peer that dies at startup fails the run in ~20 s via the progress-based stall check in AwaitReady. sweep -check reports busy ports and lingering processes per host before a sweep, and sweep warns "rebuild with 'make sweep'" when the running binary's embedded VCS revision differs from the repository HEAD.
  • File-descriptor limits. A full N-node mesh holds N−1 persistent gRPC connections per node plus the clock-sync streams. sweep prefixes every node command (and the driven sweep itself) with ulimit -Sn, controlled by -fd-limit (default 65536; 0 keeps the host default); the failure snapshot records both limits per host.
  • SSH-config footguns. SSH config is first-match-wins per key, so an empty Host bbN stanza after Host bb* cannot override anything; overriding a proxy for directly reachable hosts requires ProxyJump none in a stanza placed before the wildcard. (iago shares one jump connection per unique proxy, so a -check across many hosts behind a ProxyJump no longer trips the jump server's MaxStartups limit.)

5. Triage ladder: a slow node

For the case where a run completes but one node ran far slower than its peers, dragging down cluster aggregates and inflating tail latency and CV. The sweep's built-in defenses — the -netcheck preflight, degraded-run flagging with per-run tcp_stats, and the node-health heatmap (§2) — find the suspect for you; this ladder finds the cause. Per-node skew grows with cluster size, so reproduce with the larger configurations and -reps 3. Each step is read-only and safe on a live cluster; bbN is the suspect, bbH a known-healthy comparison host.

  1. Is the signature loss-shaped? A node behind a lossy link has p99 pinned at ~200–220 ms — the Linux minimum TCP retransmission timeout. Check the per-node latency CDF or the degraded manifest. p99 at ~200 ms means packet loss (step 2); uniformly slow at all percentiles means a host problem (step 4).
  2. Measure link loss directly. 
    ssh bbH 'ping -c 50 -i 0.1 -s 1400 -q <bbN-ip>'   # from a healthy peer
ssh bbN 'ping -c 50 -i 0.1 -q <bbH-ip>'           # reverse direction
    Any loss on a healthy LAN is abnormal (a healthy pair shows 0%). Loss from multiple sources toward the suspect places the fault on its link segment. To isolate the direction without root, compare the kernel ICMP counters in /proc/net/snmp on both endpoints (OutEchos vs InEchos, OutEchoReps vs InEchoReps): a lossy inbound path shows requests vanishing while every reply that was sent arrives.
  3. Find where the loss happens. 
    ssh bbN 'netstat -s | grep -iE "retrans|timeout" | head'
ssh bbN 'ethtool -S <iface> | grep -iE "err|drop|discard|crc" | grep -v ": 0$"'
ssh bbN 'ethtool <iface> | grep -E "Speed|Duplex|Link detected"'
ssh bbN 'ip -s link show <iface>'
    • TCPTimeouts and slow-start retransmits orders of magnitude above healthy peers (normalize by traffic volume): chronic loss confirmed.
    • rx_fcs_err_frames growing: frames corrupted on the wire — bad cable, SFP module, or switch port.
    • FCS counters not growing while loss is reproducible: packets vanish before the NIC — switch port or cable; check switch-side TX/discard counters.
    • Speed below the expected rate: renegotiation fault; try ethtool -r or reseat.
    A reboot fixes none of these; physical intervention (cable, transceiver, switch port) does.
  4. Rule out host-level causes. 
    ssh bbN 'cat /sys/devices/system/cpu/cpu*/thermal_throttle/core_throttle_count | sort | uniq -c'
ssh bbN 'paste <(cat /sys/class/thermal/thermal_zone*/type) <(cat /sys/class/thermal/thermal_zone*/temp)'
ssh bbN 'cat /sys/devices/system/cpu/cpu*/cpufreq/scaling_cur_freq | sort -n | uniq -c'
ssh bbN 'uptime; free -m'
    Growing throttle counts or package temperature near 100°C mean cooling; frequencies capped far below max mean a governor or firmware cap; high load with no benchmark running means a stray process (ps axu --sort=-%cpu | head).
  5. Look at history. The hosts run atop with 10-minute samples: 
    ssh bbN 'atopsar -r /var/log/atop/atop_<date> -b <HH:MM> -e <HH:MM> -c'   # CPU
ssh bbN 'atopsar -r /var/log/atop/atop_<date> -b <HH:MM> -e <HH:MM> -i'   # network
    This answers whether the host was busy, hot, or saturated during the exact run window.

Two link-fault signatures seen in practice (both cluster infrastructure, not gorums or benchkit bugs; both need switch-side intervention):

  • Steady loss. ~25% packet loss, rate- and size-independent, present on an idle link, entirely in the switch→host direction (the host's own transmissions were lossless); the host's FCS counters did not grow during live loss, placing the drop at or before switch egress. Signature in results: throughput at 3–7% of run median, p99 pinned at the RTO in every run. Caught by -netcheck in seconds.
  • Load-dependent loss. Loss concentrated at TCP connection setup and slow-start bursts (SYN-retransmit and slow-start-retransmit storms in tcp_stats, healthy fast-retransmit counts), invisible to an idle ping ring — the node passes -netcheck, then straggles under the sweep's connection churn, inflating apparent B/op (retransmit buffering, not real work). Caught by degraded-run flagging; confirm with step 3's counters under a short load burst.

Excluding the flaky host from -hosts is the robust operational fix until the link is repaired; no grace budget survives a genuinely broken link.

6. Open diagnostic improvements

  • Per-peer clock-sync errors. EstimateOffsets (benchkit/clocksync.go) still discards individual per-round per-peer errors and reports only "got offsets for k of N peers". Logging the last error per missing peer would distinguish "this node could not reach anyone" from "one specific peer was down".
  • Kernel events in the failure snapshot. The snapshot lacks dmesg / journalctl capture (OOM kills, NIC resets), which rotate out within a day. A time-scoped, severity-filtered capture (dmesg -T -l err --since=<run start>; journalctl -k -p err --since=...) would be compact — typically zero lines on a healthy host. Requires passing the run start time into collectFailureDiag and verifying dmesg --since support on the hosts.
  • Netcheck under load. The idle ping ring misses load-dependent loss (§5). A short bursty probe (or comparing SYN-retransmit deltas over the first run) would close the gap.
  • DNS-free WithNodeList. The sweep-side numeric-IP workaround (§4.2) leaves the core gorums behavior in place: configuration construction resolves hostnames and the server-side path panics on failure. Making normalization syntactic (or adding a pre-resolved option) is a core API change tracked in the roadmap.
